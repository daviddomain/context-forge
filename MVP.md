# ContextForge MVP – Harness Engineering Edition

# Purpose

ContextForge is a local harness-engineering tool for coding agents.

It generates a compact, deterministic and machine-readable snapshot of a local codebase so that coding agents can orient themselves faster before making changes.

The snapshot acts as an agent-readable repository map. It does not replace source files, documentation or human review.

A coding agent may use the snapshot for orientation, but must inspect the real source files before editing code.

# Core Idea

```plain text
Repository
→ Local scan command
→ Structured project snapshot as JSON
→ Coding agent uses the snapshot as orientation
→ Coding agent reads real source files before making changes
→ Coding agent validates changes with real project scripts and tests
```

# Harness Engineering Alignment

ContextForge is a repository-local harness component for coding agents.

It supports the idea that coding agents need more than prompts. They need a readable working environment with explicit structure, reliable entry points and validation mechanisms.

In the agent workflow, ContextForge acts as a map:

1. The agent reads `AGENTS.md` for working rules.
2. The agent reads `.agent-context/project.snapshot.json` for repository orientation.
3. The agent uses the snapshot to identify relevant files, routes, scripts and conventions.
4. The agent reads the real source files before making changes.
5. The agent validates changes using the repository’s actual scripts and tests.

Guiding principle:

> Give the agent a map, not a 1000-page handbook.

# MVP Goal

The MVP provides a local CLI command that scans a Next.js TypeScript project and writes a deterministic JSON snapshot to:

```plain text
.agent-context/project.snapshot.json
```

The first version focuses only on generating a useful static snapshot.

It does not provide an MCP server, persistent database, watcher, Docker setup or automatic Codex integration yet.

# Primary User

The primary user is a developer working with coding agents such as Codex.

The developer wants to give the agent a reliable overview of the repository structure, relevant files, routes, dependencies and project conventions before implementation work begins.

# Supported Project Type in MVP

The MVP supports:

- Node.js projects
- TypeScript projects
- Next.js projects using the App Router
- npm-based projects
- Local CLI execution from the repository root

# Non-Goals

The MVP explicitly does not include:

- MCP server
- SQLite or other persistent database
- Vector search
- Semantic embeddings
- Watch mode
- Docker setup
- Nuxt or Vue support
- Full AST storage
- Automatic code summaries generated by an LLM
- Automatic Codex configuration
- Git hooks
- CI integration
- Project file modification beyond writing the snapshot output
- Reading or storing secret values

# Design Principles

## 1. The repository is the source of truth

The snapshot is only an index. It may help an agent find relevant files, but the real source files remain authoritative.

A coding agent must inspect the real source files before editing code.

## 2. The snapshot is a map, not the territory

The snapshot should make the repository easier to navigate, but it must not be treated as complete truth.

It may be stale, incomplete or based on heuristics.

Tags such as `side-effect`, `schema`, `db-access`, `client-component` and `server-component` are hints, not guarantees.

## 3. Prefer compact structure over full detail

The snapshot should contain useful extracted facts, not a full representation of the codebase.

It should answer questions such as:

- What framework is used?
- Which package manager is used?
- Which scripts are available?
- Which dependencies exist?
- Which config files are present?
- Which routes exist?
- Which route handlers expose HTTP methods?
- Which files export symbols?
- Which files import other modules?
- Which files are likely client components, server components, route handlers, schemas, tests or config files?

## 4. Deterministic output

Running the scan twice without repository changes should produce stable output.

This means:

- Sort arrays consistently.
- Use stable key order where practical.
- Avoid volatile values unless intentionally included.
- Format JSON consistently.
- Do not include `generatedAt` in the deterministic MVP snapshot.

## 5. No secrets

ContextForge must never store secret values.

The MVP may detect the existence of safe config files such as `.env.example`, but it must not read or persist values from `.env`, `.env.local`, `.env.production`, `.env.development` or similar files.

## 6. Minimal and local first

The MVP should run locally, require minimal setup and avoid unnecessary infrastructure.

# Agent Usage Contract

Coding agents may use the snapshot for orientation only.

Agents must not treat the snapshot as authoritative implementation detail.

Before editing code, an agent must inspect the real source files referenced by the snapshot.

The snapshot may be stale, incomplete or heuristic.

Agents should not manually edit `.agent-context/project.snapshot.json`.

# CLI Command

The MVP should provide one command:

```bash
npm run contextforge:scan
```

This command scans the current repository and writes:

```plain text
.agent-context/project.snapshot.json
```

If `.agent-context/` does not exist, it should be created automatically.

# Suggested AGENTS.md Usage

This should be documented as a recommended snippet, but not automatically inserted by the MVP:

```markdown
## ContextForge Usage

Before starting implementation work:

1. Run `npm run contextforge:scan` if available.
2. Read `.agent-context/project.snapshot.json`.
3. Use the snapshot only to identify likely relevant files, routes, scripts and conventions.

5. Do not modify `.agent-context/project.snapshot.json` manually.
```

# Snapshot Output Shape

The MVP snapshot should roughly follow this structure:

```json
{
  "snapshotVersion": "0.1.0",
  "project": {
    "name": "example-project",
    "rootPath": ".",
    "packageManager": "npm",
    "language": "typescript",
    "framework": "next",
    "frameworkVersion": "16.0.0"
  },
  "scripts": {
    "dev": "next dev",
    "build": "next build",
    "lint": "next lint"
  },
  "dependencies": {
    "runtime": ["next", "react", "react-dom"],
    "dev": ["typescript", "eslint"]
  },
  "configs": [
    {
      "type": "typescript",
      "file": "tsconfig.json"
    },
    {
      "type": "next",
      "file": "next.config.ts"
    }
  ],
  "routes": [
    {
      "path": "/",
      "type": "page",
      "file": "app/page.tsx",
      "layouts": ["app/layout.tsx"]
    },
    {
      "path": "/api/users",
      "type": "route-handler",
      "file": "app/api/users/route.ts",
      "methods": ["GET", "POST"]
    }
  ],
  "files": [
    {
      "path": "app/page.tsx",
      "kind": "source",
      "tags": ["server-component"],
      "imports": ["@/components/home"],
      "exports": ["default"]
    }
  ],
  "symbols": [
    {
      "name": "HomePage",
      "kind": "component",
      "file": "app/page.tsx",
      "exported": true,
      "tags": ["server-component"]
    }
  ]
}
```

Important: The deterministic MVP should not include `generatedAt` by default. A timestamp may be added later behind an explicit flag or as non-deterministic metadata outside the stable snapshot.

# Snapshot Sections

## 1. Project Metadata

Extract from `package.json` and common config files:

- project name
- detected package manager
- detected language
- detected framework
- detected framework version

Package manager detection should be based on lockfiles where possible:

- `package-lock.json` → npm
- `pnpm-lock.yaml` → pnpm
- `yarn.lock` → yarn

For the MVP, npm is the only supported package manager. Other package managers may be detected but do not need full support.

## 2. Scripts

Extract scripts from `package.json`.

Important scripts for coding agents include:

- dev
- build
- lint
- test
- test:e2e
- typecheck
- db:migrate
- codegen

The scanner should include all scripts, not only known ones.

## 3. Dependencies

Extract dependencies from `package.json`:

- `dependencies`
- `devDependencies`

The MVP should store dependency names. Versions may be included, but the output should remain compact.

## 4. Config Files

Detect common project config files, including:

- `package.json`
- `tsconfig.json`
- `next.config.js`
- `next.config.mjs`
- `next.config.ts`
- `eslint.config.js`
- `eslint.config.mjs`
- `components.json`
- `tailwind.config.js`
- `tailwind.config.ts`
- `postcss.config.js`
- `.env.example`

Secret-bearing env files must not be read or included with values.

## 5. Next.js App Router Routes

Scan the `app/` directory.

Detect:

- pages via `page.tsx`, `page.ts`, `page.jsx`, `page.js`
- layouts via `layout.tsx`, `layout.ts`, `layout.jsx`, `layout.js`
- route handlers via `route.ts`, `route.js`
- dynamic segments such as `[id]`
- catch-all segments such as `[...slug]`
- optional catch-all segments such as `[[...slug]]`
- route groups such as `(dashboard)` without including them in the public path

For route handlers, detect exported HTTP methods:

- GET
- POST
- PUT
- PATCH
- DELETE
- HEAD
- OPTIONS

## 6. File Index

Scan relevant source files:

- `.ts`
- `.tsx`
- `.js`
- `.jsx`

Exclude:

- `node_modules/`
- `.next/`
- `dist/`
- `build/`
- `.git/`
- `.agent-context/`

For each file, collect:

- relative path
- file kind
- tags
- imports
- exports

## 7. Symbol Index

Extract a lightweight symbol index.

Possible symbol kinds:

- component
- function
- constant
- type
- interface
- schema
- unknown

The MVP does not need to store function bodies.

## 8. Tags

Apply simple heuristic tags where possible:

- `client-component` when file starts with `"use client"` or `'use client'`
- `server-component` for App Router page/layout components without `use client`
- `route-handler` for `route.ts` or `route.js`
- `config` for known config files
- `test` for test/spec files
- `schema` for files that appear to define validation schemas
- `db-access` for files importing known DB utilities or packages
- `side-effect` for obvious side-effect usage such as `fetch`, `process.env`, `new Date`, filesystem imports or database imports

The tags are heuristic and must not be treated as guaranteed truth.

# Technical Recommendations

Recommended packages for the MVP:

- `tsx` for running TypeScript locally
- `fast-glob` for file scanning
- `ts-morph` for TypeScript/JavaScript parsing
- `zod` for snapshot schema validation

The implementation should avoid unnecessary dependencies.

# Error Handling

The CLI should fail with a clear error message if:

- `package.json` is missing
- the current directory does not look like a supported project
- snapshot writing fails

The CLI should not fail only because optional files are missing.

For example, a project without `app/` may still produce a partial snapshot, but it should warn that no Next.js App Router directory was found.

# Security Rules

The MVP must follow these rules:

- Do not read secret env values.
- Do not include `.env.local`, `.env.production`, `.env.development` contents.
- Do not execute project scripts during scanning.
- Do not modify project source files.
- Do not send data to external services.
- Do not require network access.

# Acceptance Criteria

The MVP is complete when:

- `npm run contextforge:scan` exists.
- Running the command creates `.agent-context/project.snapshot.json`.
- The snapshot includes project metadata.
- The snapshot includes package scripts.
- The snapshot includes runtime and dev dependency names.
- The snapshot includes detected config files.
- The snapshot includes Next.js App Router pages.
- The snapshot includes route handlers and exported HTTP methods.
- The snapshot includes a lightweight file index.
- The snapshot includes imports and exports per scanned file.
- The snapshot includes a lightweight symbol index.
- The snapshot output is deterministic across repeated runs without code changes.
- The snapshot does not include `generatedAt` by default.
- The scanner does not persist secret values.
- The README briefly explains how to run the scan and what the snapshot is for.
- The README includes the agent usage contract.
- The README includes a suggested `AGENTS.md` usage snippet.

# Validation Commands

Recommended validation commands:

```bash
npm run contextforge:scan
npm run build
npm run lint
```

If build or lint do not exist in the host project, this should be documented instead of invented.

# Open Questions

- Should ContextForge be embedded into each repository or installed as a reusable package?
- Should the snapshot schema be strict from the beginning or allowed to evolve quickly during early experimentation?
- Should generated snapshots be committed to Git or treated as local cache only?
- Should `generatedAt` stay excluded from deterministic output or exist only behind an explicit flag?
- Should the MVP include file hashes immediately or only in the later staleness-check version?
- Should route detection support `src/app/` in addition to `app/` in v0.1?

# Short Strategic Summary

ContextForge is not just a scanner.

It is a practical harness-engineering component for agentic coding.

Its value is that it converts repository structure into explicit, compact data that a coding agent can use before implementation work begins.

The long-term goal is not to replace human judgment or source-code inspection, but to reduce orientation cost, avoid blind repo exploration and make repositories more agent-readable.
