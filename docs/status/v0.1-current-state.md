# ContextForge v0.1 Current State

## Purpose

ContextForge v0.1 is a local Node.js and TypeScript CLI for generating a
compact, deterministic project snapshot for coding agents.

The current focus is a static repository map for Next.js TypeScript projects,
especially projects using the App Router. It is meant to reduce orientation
cost before implementation work begins.

## Snapshot Role

The generated `.agent-context/project.snapshot.json` is an agent-readable
orientation map. It helps identify likely project structure, scripts,
dependencies, routes, source files, imports, exports, symbols and heuristic
tags.

The snapshot is not the source of truth. It may be stale, incomplete or based on
heuristics. Coding agents must still inspect the real source files before making
implementation changes.

## Current Scanner Capabilities

The v0.1 scanner currently:

- Reads `package.json` and extracts project metadata, scripts, runtime
  dependencies and development dependencies.
- Detects safe common configuration files such as `package.json`,
  `tsconfig.json`, Next.js, ESLint, Tailwind, PostCSS, `components.json` and
  `.env.example`.
- Scans Next.js App Router routes from both `app/` and `src/app/`.
- Detects App Router pages, layouts, route groups, dynamic segments, catch-all
  segments and optional catch-all segments.
- Detects route handlers and exported HTTP methods, including delegated method
  exports.
- Builds a lightweight source-file index for `.ts`, `.tsx`, `.js` and `.jsx`
  files while excluding generated and dependency directories.
- Extracts static imports, side-effect imports, dynamic imports, re-exports and
  compact export names.
- Builds a lightweight symbol index for components, functions, constants,
  types, interfaces, schemas and unknown symbols.
- Applies heuristic tags such as `client-component`, `server-component`,
  `route-handler`, `config`, `test`, `schema`, `db-access` and `side-effect`.
- Writes deterministic formatted JSON without `generatedAt` by default.

## Dogfooding So Far

ContextForge has been dogfooded on the Personalfragebogen / EP Films Connect
project, a real Next.js TypeScript App Router application. That run confirmed
that the snapshot was useful for orienting agents around metadata, scripts,
dependencies, config files, routes, layouts, source files, symbols and heuristic
tags. A repeated scan without repository changes produced stable output for the
tested target.

ContextForge has also been dogfooded on the e+p films website project, a real
Next.js TypeScript project that uses `src/app`. That run confirmed that routes
from `src/app` are detected and that public route paths do not include the
physical `src` prefix.

Both dogfooding runs treated the snapshot as an orientation aid only. Real
source files remained authoritative for implementation decisions.

## Recent Scanner Hardening

Recent v0.1 hardening work added or verified:

- Next.js App Router scanning for both root-level `app/` and `src/app/`.
- Delegated route handler HTTP method detection.
- Improved symbol kind detection for uppercase constants and route-handler
  functions.
- Known Jest and Sanity source-file config classification for `jest.config.ts`,
  `sanity.config.ts` and `sanity.cli.ts`.
- Avoiding misleading React component tags on known config files, even if a
  config file contains a `"use client"` directive.
- Sanity schema file tagging for common `sanity/schemaTypes/**` and
  `src/sanity/schemaTypes/**` paths.

## Current Non-Goals

The current v0.1 phase does not include:

- Scanner behavior changes beyond dedicated, narrow hardening tasks.
- Snapshot schema expansion for explanatory metadata.
- Manual edits to generated `.agent-context/project.snapshot.json` files.
- MCP server support.
- SQLite or another persistent database.
- Watch mode.
- Vector search.
- Docker setup.
- Git hooks or CI setup.
- Publishing ContextForge as a package.
- Treating generated snapshots as a replacement for source-code inspection.

## Possible Next Candidates

Sensible future candidates include:

- Add `tagReasons` or a similar explanatory mechanism for why heuristic tags
  were assigned.
- Continue refining noisy `side-effect` tags.
- Expand scanner coverage only when concrete dogfooding findings justify it.
- Improve status and usage documentation as v0.1 behavior stabilizes.

These are candidates only. They are not part of the current v0.1 status
document task and do not define a snapshot schema change.
